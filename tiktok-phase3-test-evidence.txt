1. UMGESETZT (nur src/ai/tiktok.ts + src/ai/server.ts + src/routes/app/tiktok.tsx + i18n de/en)
=======================================================================
- Diagnose-Feld `lengthRecommendation` { seconds, structure, reason } — eigenständiges
  strukturiertes Feld mit empfohlener Länge (Sekunden) + Aufbau (Hook-Phase/Inhalt/CTA) +
  Zahlenbegründung (reason referenziert echte Nutzerzahlen + berechnete Retention).
- Deterministische Retention-Rechnung `computeRetention(metrics)` — reine Funktion, KEINE LLM:
  avgWatchSeconds, watchRatePct (avgWatch/length), totalWatchSeconds (views×avgWatch);
  Division-durch-0-Guard (length==0/unparsbar/fehlend → null). Der Prompt erhält einen
  „Berechnete Retention"-Block NUR aus Nutzerangaben (EINZIGE zusätzlich erlaubte Zahlenbasis).
- `parseLengthSeconds` — '42s' | '42 Sekunden' | '0:42' | '1:05' | '42'; '0s'/''/undefined/garstig → undefined.
- Pflichtfelder views+length+avgWatch: UI (missingDiagnoseMetrics in tiktok.tsx) + Server-Validator
  (server.ts nutzt dieselbe geprüfte diagnoseRetentionGaps-Funktion) + Engine-Short-Circuit.
- Ehrlicher „zu wenig Daten"-Zustand: fehlen views/length/avgWatch (oder Länge unparsbar),
  KEIN LLM-Call (deterministisch), Output { dataGap: true, missingMetrics[], note, cta } — note sagt
  ehrlich, was ohne die Daten nicht beurteilt werden kann, cta nennt die zu ergänzenden Felder.
  Keine erfundene Zahl/Länge.
- SelfCheck Q6 `lengthGrounded` (de+en) als HARD-REJECT-Kriterium: Begründet lengthRecommendation.reason
  die Länge an ECHTEN Nutzerzahlen/berechneter Retention statt generischem Default („8–20s sind am
  besten")? Nur explizites false rejected; fehlendes Flag (alte Modelle/Outputs) = unbekannt → pass,
  damit die Regression stabil bleibt.
- Retry-Hint (de+en) verlangt das neue Feld explizit + „alle sechs selfCheck-Booleans".
- UI: eigenes Panel „Nicht genug Daten für eine vollständige Diagnose" (note+cta) bzw.
  „Längen- & Aufbau-Empfehlung" (Sekunden/Struktur/Begründung). Alle Texte in de+en.
